# CLI 指南

Rover 中的主要用户入口点是 CLI。它允许用户创建和管理任务。大多数现有命令专注于处理任务及其生命周期。我们的 CLI 应该向用户提供相关信息，引导他们使用编码 agent，并提供当前任务的可见性。

## 原则

这些原则是强制性的，影响此存储库中的所有 CLI 项目，包括 `packages/cli` 和 `packages/agent` 项目。

1. CLI 必须有用。始终显示相关且简洁的信息
2. 输出在命名、风格、语气和输出方面必须一致
3. 保持用户参与。尽可能流式传输信息，并为长时间运行的任务显示加载器
4. 提供友好的问题和输出，同时看起来专业

## 语气

我们设计的 CLI 必须帮助用户完成任务。用户必须感到有效率，我们应该避免任何形式的挫败感。为此，CLI 的语气和风格应遵循这些规则：

1. 在需要时使用简短明了的描述
2. 要简洁
3. 命令、参数、选项和输出之间的命名必须一致
4. 使用友好的语气
5. 更喜欢对话而不是直接提问
6. 避免过度使用表情符号。仅使用它们来突出相关信息或个性化 Rover

## 颜色

- 默认颜色（无颜色）：常规文本
- 青色：标题
- 紫色：主要信息。每个部分只有一个元素
- 灰色：属性和不太相关的信息
- 绿色：成功的响应
- 黄色：正在进行的工作和警告信息
- 红色：失败的操作和错误

## 命令

为了定义命令，我们明确区分两个级别：

1. **主命令**：它们是默认 Rover 流程的一部分：在项目中初始化 Rover、创建任务和合并它。它们位于顶层并分成几个部分
2. **子命令**：提供额外功能，如管理配置和工作流

任何命令的命名约定是：

- 主命令和子命令必须简短
- 主命令始终引用"任务"的概念，这是顶级资源
- 子命令必须是表示资源的名词（config、workflows 等）。根据资源区分单数和复数
- 对于主命令和子命令，更喜欢使用动词而不是名词
- 命令必须在资源之间保持一致。如果我们想重命名或删除命令，我们应该一次性弃用所有
  - `new`
  - `list`
  - `inspect`
  - `delete`
  - `update`

### 例外

有一些不一致之处我们将来可能会更改。我将在这里记录它们以供将来参考：

- `task` 命令不一致。它应该是 `new` 或 `create`

### 参数和选项

参数和选项扩展每个命令的配置。它们应该清晰、简洁且在上下文中。一些要遵循的规则：

- 对主命令输入使用参数（`<task id>`）
- 对强制字段始终使用参数（`<task id>`）
- 对可能稍后询问或不需要运行某个命令的信息，在末尾使用可选参数（`[task description]`）
- 对任何更改默认命令行为的输入使用选项（`--yes`）。尽可能提供短选项和长选项（不存在冲突时）
- 对选项使用描述性名称并添加替代的较短版本（`--source-branch | -s`）
- 将全局选项放在 CLI 级别（`--debug`）
- 在所有命令中使用一致的选项和参数名称（`task id`）

## 模式

常见模式的规则和示例。

### 标题头

标题头是出现在任何命令输出之前的部分。这里，我们有两种类型的标题头：

- 启动画面：它显示带有渐变的"ROVER"文本。仅用于配置 Rover 项目（`rover init`）。
- 常规：它显示 CLI 名称、版本和当前上下文：

  ```
  Rover (v1.3.0) · /home/user/workspace/project
  ---------------------------------------------
  ```

### 标题

标题突出显示 CLI 输出中的单独部分。它使用粗体青色文本，并在其前面有换行符。

```

Title
-----
```

为了保持输出清晰，我们应该减少单个输出中的部分数量。要简洁明了。

### 列表

列表枚举相关元素。这里，我们应该区分三种不同类型的列表：

- 属性：一组相关元素的标题 + 描述。一些示例是同一对象的属性。在这种情况下，我们使用灰色文本显示标题，白色显示值，并用 `·` 符号作为列表项的前缀：

  ```
  · ID: 76
  · Title: Update the AGENTS.md file.
  · Description: |
    This is a longer value that might spawn multiple lines.
    We show it using the | decorator on the property name.
  ```

- 独立元素：表示独立实体的元素列表。例如，文件列表。这里，我们使用列表符号 `├──` 和 `└──`。

  ```
  Iteration Files 1/1
  ├── changes.md
  ├── context.md
  ├── plan.md
  └── summary.md
  ```

- 过程：按顺序完成并具有关联元数据的步骤列表。例如，创建任务的过程（创建分支 + worktree，运行容器等）。在这种情况下，我们添加一个标题部分和其下的边框。然后，我们按照日志格式显示正在处理的步骤：

  ```
  Run the task in the background
  ------------------------------
  ● 12:30 | Created the rover/task-123jhksdna branch and worktree
  ○ 12:31 | Starting the rover-task-44-1 container
  ```

  圆圈的颜色取决于步骤状态。如果正在进行中，使用青色。如果完成，成功使用绿色，失败使用红色。

  **过程将在可能的情况下位于命令输出的末尾**。

### 文件内容

对于文件内容，我们将内容显示为一个框。标题将是文件名。我们将使用 [`boxen` 库](https://github.com/sindresorhus/boxen) 来实现这一点。

```
┌ context.md ─────┐
│ foo bar foo bar │
└─────────────────┘
```

### 提示

提示帮助用户理解当前上下文中的下一步或相关操作。为了有帮助，我们需要限制它们，因为长列表会被忽略。

提示的约定是：

1. 当有明确的下一步时，只显示一个提示
2. 避免显示超过两个提示
3. 提示消息必须简洁
4. 如果替代操作不是明显相关的，跳过提示
5. 始终在底部显示提示
6. 使用以下格式的提示。对"Tip:"文本使用青色，对其余部分使用灰色

```

Tip: run `rover logs 12` to check logs
```

## 始终避免

这些是强制性规则。不遵循它们将为我们的用户造成非常糟糕的用户体验。

- 不要为常规文本设置颜色。避免使用 `color.white` 帮助器，因为它们在浅色终端上看起来会很糟糕。
- 不要过度使用表情符号
